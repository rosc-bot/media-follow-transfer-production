# 0.1.1 生产修复发布候选

本次采用线上既有源码作为基线，保留 GitHub main 原有历史，先记录生产源码同步提交，再独立提交审计修复和版本递增。没有重建仓库或强制推送。

## 修复范围

- 明确业务码优先判断成功；117 认证刷新有界并持久化；157 容量不足正确终止。
- 修正零基页码的 total/totalPages 边界，落盘 readback 复用同一认证刷新上下文。
- 隔离 hydration 毒任务，保留领取计数并回滚半成品修改；后续任务可领取。
- 排除带 NEEDS_REVIEW 的队列条目；暂停读取不再受 ORM identity map 陈旧值影响。
- 进程启动只恢复真正过期锁，不抢占其它实例的新领取；测试注入入口不启真实心跳和多 worker。
- 显式 readback 集号映射不完整时隔离该任务；库存闭环失败保留已落盘执行阶段，不重放云盘恢复，不暂停全局。
- 保证确认的 4K WEB-DL 优先于 1080p REMUX，文件选择与跨分享质量比较一致；未知分辨率 REMUX 保留原有保守保护。
- 实盘完整扫描确认缺失允许补库，但旧账本不能绕过同集执行中任务。
- 完结归档覆盖 TMDB 全部季且依赖权威状态；历史目录发现和主产国分类保持身份及生命周期边界。
- 合理保留已有文件命名规范，修正未知来源及 Atmos 标识等边界。
- 通知测试只在 HTTP I/O 阻止真实 Telegram 请求，不遮蔽路由、卡片和结果逻辑；公开发布失败不再记录成功。
- 修复完结剧仅有 Inventory 而缺资源质量记录时的 CloudDiskInventory 未导入错误。

## 验证与限制

开发副本 Python 3.11 回归 381 项全通过，致命静态检查与编译通过。发布前还需在生产同版本 Python 镜像内跑完整回归和隔离 PostgreSQL 验证；候选的通过不等于已上线。

没有数据库模型或迁移变更；生产数据库迁移版本与源码 head 均为 0013_telegram_roles_and_admins。生产只读核对，测试 DDL/DML 仅允许独立的 verification 数据库。

全量 Mypy 存在历史类型欠债：基线 205 项，本次 198 项，无新增错误。完整 Ruff 也有旧风格/宽泛异常处理提示；本次通过的门槛是致命错误检查，并未宣称全量风格和类型检查通过。因此本次为经业务回归验证的生产修复发布，不创建正式 GitHub Release/标签，不把缺少全量类型验收包装成完整正式发布。

## 发布边界

- 不修改凭据、网盘容量、会员状态、频率、并发度、暂停开关或历史队列记录。
- 保留当前 global_pause=0、follow_paused=1、transfer_paused=1。
- 不向正式频道发送测试消息，不触发真实网盘转存验收。
- 构建复用线上既有 Python/依赖底座，替换经过验证的代码；持久会话和数据库仍使用现有卷。
- 监听若因入库模块修复而需更新，只更换原有容器，严禁启动第二个 Telethon 客户端。实际停止和恢复时间必须以日志报告，不能宣称绝对零中断。
- RELEASE_COMMIT 是构建时由明确 Git SHA 生成的运行标记，不再把历史生成文件作为 Git 版本源；唯一版本源仍为 pyproject.toml。

回滚保留原源码压缩包和各服务原镜像 ID；不迁移、不删库、不删网盘文件。实际版本/哈希/健康与监听连接结果由上线后单独回读记录。
